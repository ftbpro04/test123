# LTX 2.3 exact workflow · CUDA 13

Implementation for `10E_I2V_triplepass_00010-audio.mp4.json`.
**Review build, not a production-certified or published image.** See `VALIDATION.md` for measured status and remaining blockers.

## Workflow completeness

The parser finds **16 unique configured model files**, including all bypassed selections and all seven Power LoRAs (six disabled). It inspects 93 root nodes and two subgraph nodes. Two catalog references and four historical references are recorded separately; they do not add downloads. The selected upscaler is **2.3 x2 1.1**, not the historical 2.0 x2 1.0 catalog entry.

`workflows/original.json` preserves the source. `workflows/ltx23-linux.json` only normalizes two Power LoRA backslash paths. It does not change prompts, strengths, toggles, graph links, generation settings, or model selections. The workflow still needs your input image (`seedvr2__02471_.png` was not supplied) and a prompt. Original previews are metadata, not bundled videos.

Source of truth: `model_manifest.json`; selections and occurrence classifications are generated by `workflow_model_parser.py`. `workflow_inventory.json` also records node metadata. `node_manifest.json` pins every installed repository. The original LTXVideo metadata has two revisions; the selected existing pin contains all four referenced LTXVideo node classes, but only actual registration/runtime testing establishes compatibility.

## Architecture

`tini → entrypoint.sh → supervisor.py` starts the independent dashboard first, then the locked downloader, Jupyter, and exactly one ComfyUI process. A Torch probe runs separately. ComfyUI, Jupyter, and downloader exits are recorded, not automatically restarted. Only the dashboard gets a two-second watchdog. SIGTERM is forwarded to process groups; a second supervisor refuses to duplicate services.

Application: `/opt/ComfyUI`. Runtime scripts: `/opt/ltx23`. Only `models`, `input`, `output`, and `user` are symlinked to `/workspace/ltx23-data`. The normalized workflow is installed under `user/default/workflows` once and is never overwritten on restart. Unknown existing application data is preserved and causes a visible setup error rather than being deleted.

Models are **not** included in Docker. Python, custom node sources, Torch/Triton caches and HF caches are disposable. The automatic downloader bypasses HF caches entirely. Optional downloader extensions may create their own downloads; storage auditing includes legacy directories, but no script automatically deletes user data.

The Docker build constrains Torch, torchvision, torchaudio (if present), and Triton to their base-image versions during dependency installation. After **all** packages are installed it checks Torch 2.10.x, CUDA 13.x and cuDNN 9, runs `pip check`, records package versions, and verifies the complete manifest. The GPU driver still needs to support CUDA 13.0+.

## Downloads and verification

One nonblocking filesystem lock serializes automatic downloaders. Each destination has one deterministic `.part` and identity record under `downloads/`. Range resumes validate Content-Range. Servers ignoring Range cause a safe restart. Retries are bounded. Free space is checked before transfer and during streaming; default reserve is **10 GiB**. SHA256 and exact size are verified before an atomic rename. Downloads and models must share a filesystem.

Every existing file is locally SHA256 checked on restart. Verified files require **zero HTTP requests and zero model download bytes**, though hashing 100+ GB takes disk I/O. Incomplete targets are resumed; wrong hashes are re-downloaded. Existing unknown or mismatched partial identities fail visibly rather than being silently discarded. The metadata cache is small JSON, not another model copy.

`DOWNLOAD_WORKFLOW_MODELS=0` performs a local check without downloading; it does not pretend absent files are ready. Automatic retries after a failed launch require an explicit restart or running `/opt/ltx23/download_workflow_models.py` manually. Do not launch a second full supervisor to restart just one service.

### Source limitations

Ten files have author/maintainer repository metadata. Five additional files have matching names, exact sizes and SHA256 from HF mirrors, with candidate Civitai author/version links recorded. **Their mirror hashes have not been compared to authoritative Civitai hashes.** They are clearly marked `source_verified: false`. No similarly named replacement was substituted.

`animeflatLTX.2.3.safetensors` remains mandatory but its exact size and SHA256 are unresolved. Candidate Civitai version **2809357** could not be read (HTTP 403). At runtime the downloader can resolve that version using `CIVITAI_TOKEN`, requires exactly the selected filename, obtains the API SHA256 and exact response byte length, then downloads/verifies it. If it still cannot access the source, the result stays **15/16 or less**, with an explicit error. Access requirements have not been confirmed; a token may not resolve every access restriction.

Do not call this a ready-to-use complete pack until all source checks and real GPU tests pass. `python /opt/ltx23/check_build.py --require-sources` intentionally blocks release while author-source verification remains unresolved.

## Dashboard and access

Dashboard 18080, ComfyUI 8188, Jupyter 8888. `/api/health` reflects only the dashboard. The UI shows process identity plus listener status, all models, download/reuse bytes, GPU/driver/Torch CUDA, filesystem totals, per-directory physical usage, legacy folders, validation and six rotating logs. Scans skip symlinks and count hardlinks once. Filesystem totals may include unrelated host data; per-directory totals explain the actual workspace allocation.

Launch URLs use `PUBLIC_IPADDR` and `VAST_TCP_PORT_<internal>`. A missing mapping disables its button, rather than guessing the internal port is public. `COMFY_PUBLIC_URL` / `JUPYTER_PUBLIC_URL` can override proxy URLs. These are optional, not required for normal mapped Vast ports.

Jupyter creates a random persistent token at `/workspace/.jupyter_token` (mode 0600); it is omitted from process arguments and redacted from dashboard logs. On a public unauthenticated dashboard, the launch button does not reveal the token. Retrieve it in the Vast console with `cat /workspace/.jupyter_token`. If `DASHBOARD_PASSWORD` is configured, sign in as `ltx23`; the authenticated Jupyter button includes the token. Direct ComfyUI has its normal unauthenticated server behavior; use your normal Vast network access controls.
